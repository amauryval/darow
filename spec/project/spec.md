document states its contracts. It changes only when the repository changes.

Its sections are indexed by title in [`spec/index.md`](../index.md) — the entry point to the three

same change.**

## 0. Non-negotiable rules

1. **One product, one name.** The name appears in the module path, the binary, the API title, the
   UI header, the container image and the documentation. Any divergence is a finding, not a
   variant.
2. **English in everything written for a reader of the repository.** `README`, `LICENSE` and the
   whole of `spec/` — the three domains — are in English. The product's user-facing strings are a
   separate matter: the UI is monolingual French (`spec/front/spec.md` §0.17).
3. **Generated artefacts are never hand-edited.** `docs/` (Swagger) and `internal/webui/dist/`
   (UI build) are outputs, regenerated by their task.
4. **Every task goes through `mise`.** A command a contributor must run is a `mise` task, declared
   in `mise.toml`, and CI runs the same tasks.
5. **No task enumerates `./...` unfiltered.** The module tree contains an npm-shipped Go package
   under `web/node_modules/`; every Go task filters the package list explicitly.
6. **The documentation tree is closed.** Three domains — `back`, `front`, `project` — each with the
   same five files, all always present, even empty.

## 3. Toolchain

Pinned in `mise.toml`: Go 1.26.4, Node 22, `swag` 1.16.6. `./bin` is prepended to `PATH`, and
`CGO_LDFLAGS` is forced empty so the DuckDB driver links regardless of the host shell profile.

## 4. Tasks

| Task | Does |
|---|---|
| `test` / `test-race` | the Go suite, plain and under the race detector |
| `lint` | `go vet` plus a `gofmt` check, scoped to `cmd internal docs` |
| `docs` | regenerates Swagger from the handler annotations |
| `ui-install` / `ui-build` / `ui-dev` | UI dependencies / production build into `internal/webui/dist` / Vite dev server |
| `ui-lint` / `ui-test` | eslint / vitest on the UI |
| `build` | the server binary, after regenerating docs and UI |
| `run-dev` | runs the server against `config.yaml`, after regenerating docs and UI |

`ui-dev` and `run-dev` are the developer's to launch, never an agent's.

## 5. Build and distribution

`Dockerfile` is a three-stage build: Node 22 builds the UI into the embed directory, Go 1.26
compiles the single binary (stripped, `-ldflags="-s -w"`), and a `gcr.io/distroless/cc-debian12:nonroot`
runtime carries it — glibc, libstdc++ and ca-certificates, no shell or package manager, running as
the image's built-in uid/gid 65532. The image exposes 8080 and its entrypoint is the binary.
Configuration and the working directory come from outside the image.

## 6. Continuous integration

`.github/workflows/ci.yml` runs, on every push and pull request: `go vet` and `gofmt`,
`go test -race`, then `ui-lint`, `ui-test` and `ui-build`, then the Docker image build. A red check
is a blocker, recorded in the domain it belongs to.

## 7. Documentation

Three audiences, three places:

-   **The user** — what the product does, how to run it, how to configure it. The root `README`
    is the prose entry point; `config.yaml` and the Swagger UI served under `/swagger` complete it.
-   **The contributor** — layout, tasks, conventions. The root `README` and `.claude/CLAUDE.md`.
-   **The agent** — `.claude/CLAUDE.md`, the skills under `.claude/skills/`, and `spec/`.

`spec/` never documents the past: each file states the present, and a landed chantier leaves it.
