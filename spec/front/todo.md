# Darow — Identified debt (Vue 3 UI)

> **Role** — the chantiers to run on `web/`: gaps between the rules of
> [spec.md](spec.md) and the state of the code. Each row is a chantier, not a tolerated
> exception.
> What breaks a feature goes to [blockers.md](blockers.md); what is accepted to
> [limitations.md](limitations.md); what is not decided yet to
> [improvements.md](improvements.md).
>
> Go server: [../back/todo.md](../back/todo.md) · Project: [../project/todo.md](../project/todo.md).

Each entry carries a stable identifier (`TODO-Fn`); a retired identifier is never reused. Entries are
grouped by nature, in decreasing order of impact within each group.

**How much to write.** An entry may be long. Detail is welcome here — it is what makes the chantier
implementable months later, by someone with no memory of the audit that found it: name the files and
the components concerned, say what to change and in what order, state the rules and invariants to
respect, and record the trap that produced the gap. Naming what exists is part of that: a component,
a composable, a type, a prop or an event are cited by name — that is a pointer into the code, not
code. Cite the file and the symbol, never a line number: it is stale the next time anyone touches
the file, and a wrong line sends the reader to the wrong place with confidence. A symbol is found by
search and stays true. What stays out is **code itself**: no snippet, no template fragment, no diff. Write the
instruction, not the patch — the code is written later, against the code as it is then.

**Every chantier here is responsive**, on the same terms as the rest of the UI, and lands only once
`mise run ui-build` (type-check) and `mise run ui-lint` pass — a type error is part of the chantier,
not a follow-up.

**Server-dependent chantiers.** TODO-F35, TODO-F37, TODO-F38 and TODO-F44 each have a server side
that must exist first — `../back/todo.md` TODO-8, TODO-14, TODO-13 and TODO-18 respectively; none of
them can be started against the API as it is today.

## 1. Architecture and code

| # | Chantier |
|---|---|
| TODO-F35 | Realign `src/client/` on the single success envelope the server adopts (`../back/todo.md` TODO-8), which is a **breaking** change to every write route at once. Today each wrapper in `src/client/tables.ts`, `sources.ts` and `filters.ts` mirrors an envelope the server invented per route, and `src/client/types.ts` carries one DTO per shape; three routes resolve to `undefined` because a `204` and an empty body do so in `http.ts`, so nothing downstream can say what was deleted. The worst of it is `uploadSource`: `useSources.upload` tells a loaded upload from an unloaded multi-layer GeoPackage by probing for a `tableId` field on the response, and returns `{ tableId }` or `null` accordingly — a shape difference read as a discriminator, which the server side of the chantier replaces with an explicit one. Order: `types.ts` first (the one envelope type plus the discriminated upload outcome, §2 — no response type is ever declared in a resource module), then the wrappers, then the callers. The callers are where the gain lands: `useSources.upload` stops probing and switches on the discriminator; the delete flows in `useSources`, `useTableMetadata` and `useSavedFilters` can finally toast **what** was removed instead of a generic success, which is what §8.4 asks of a global action's result and what §8.3 asks of a destructive one. Two things stay out of the envelope and out of this chantier: the tile bytes and the streamed export, neither of which is JSON. Run it in one pass with TODO-F38, whose server side (`../back/todo.md` TODO-13) is the same breaking release |

## 2. User experience

| # | Chantier |
|---|---|
| TODO-F44 | Give a column a *Mise à jour* action, once the server offers one (`../back/todo.md` TODO-18): rewrite a column's values in place — concatenate, compute, assign per condition — over the rows a filter names. Today nothing on the screen changes more than one value at a time: `AddColumnModal` creates a column and leaves it empty with no way to fill it, `ColumnsModal` only toggles visibility, and the edit session rewrites one cell at a time (`TableRowEditCell`, drafts held by `useRowEdits`), which stops being usable past a screenful and cannot express "toutes les lignes". The only existing path is *Dériver* (`DeriveTableModal`, `DeriveFromTableForm`'s computed columns), and it answers a different question: it produces a **second table** — new identifier, no stored filters, no per-table settings — where the user wanted this one corrected. Where it goes: on the column itself, through a menu on the grid's column header in `TableDataPanel`/`TableRowsPanel`, not inside `ColumnsModal` — that modal is opened from `TableToolbar`'s *Affichage* group and means "what is displayed", and hanging an irreversible data write off it mixes exactly the registers §8.9 separates. New pieces: `TransformColumnModal.vue` under `components/tables/`, a `useColumnTransform` composable holding the draft, the preview and the submit (§0.2 — the modal is wiring and rendering only), the client wrappers and their DTOs in `src/client/` (§2: the response types in `types.ts`, never in the resource module). What is reused as is: `FilterNodeEditor` for the rows kept **and** for each case's own conditions — a case is a condition tree plus an assignment, and it is the same tree in both places; `useColumnDistinctValues` to offer a column's existing values when assigning against them, which is what "selon les valeurs existantes" means on screen; `DeriveFromTableForm`'s alias/expression row as the model for the free-expression arm. Two rules shape the form. The arms offered follow the column's type, already in hand through `useTableMetadata`'s `columns` — arithmetic only where the type takes it — and an inapplicable arm is made **unrepresentable** rather than left for the server to refuse, the same trap TODO-F37 records. And no SQL is ever assembled in the client (§0.1's spirit and the reason the guided derivation exists at all): the arms are posted structurally, the free-expression arm posts the user's text verbatim and never wraps or concatenates it. The write is irreversible and reaches every matching row, so §8.3 applies in full: the modal shows the server's preview — the number of rows that will change and a before/after sample — as its own four states (§0.18), confirms against that number before applying, shows a busy state on submit (§8.2), and toasts how many rows were written (§8.4). On success, reload the current page through `useTableRows` **and** refresh the map layer (`useMvtLayer`): the tiles are keyed on the table's `UpdatedAt`, so a layer left alone keeps drawing the attributes that were just replaced |
| TODO-F31 | `views/TableDetailView.vue` has no loading and no error state: every child is behind `v-if="table"`, and `useTableMetadata.loadAll` swallows a failure into a toast alone. A table whose metadata fails to load — or is merely slow — shows a breadcrumb over a blank page, and the only way back is a browser reload, which §0.18 and §8.1 both forbid (four explicit states, an error carrying a way to retry without reloading). Have `useTableMetadata` expose its `loading` and its `error` alongside `table` and `columns` instead of toasting, and have the view render `Skeleton` on the first load and `ErrorState` with a retry on the failure, the way `SourcesView` and `TableRowsPanel` already do. Keep the toast for the *mutating* actions (rename, delete, add column), where §8.4 puts a global action's result — it is only the load whose error has to stay on screen |
| TODO-F32 | Opening a modal moves focus to its ✕ close button rather than to its first meaningful field, against §8.5: `useFocusTrap.activate` focuses the first focusable element of the container, and `Modal.vue` renders the close button in its header, before the slot. So `Ajouter une colonne`, `Créer un filtre` and `Dériver une table` all open with the destructive-adjacent control focused and the user has to Tab into the form. Fix it in the trap rather than in each modal: focus the first focusable that is not the close control — mark that control so the trap can skip it — and keep the current behaviour for a modal whose slot has no focusable content at all (`GeometryModal`, `ConfirmDialog`). The Tab/Shift+Tab cycle and the focus restore on close stay as they are |
| TODO-F37 | Give the derivation modal an aggregation mode, once the server offers one (`../back/todo.md` TODO-14): group-by columns plus aggregate expressions. *Dériver* currently produces one derived row per source row, and grouping is the other thing a user derives for. It needs its own screen rather than a third tab on `DeriveTableModal`, whose column picker means "carry this column over" and would mean "group by this column" in the new mode — the same word for two different acts is exactly the confusion the guided mode was built to remove. What can be reused as is: `useDeriveTable` for the submit and the new table's name, `FilterNodeEditor` for the row conditions (the same tree, in the same place in the sequence), and the picker's exclusion of the geometry column and `__pkey`. What is new: the group-by column list and the aggregate rows, an aggregate row being an expression under an alias like `DeriveFromTableForm`'s computed-column rows already are. Trap: under a `GROUP BY` a column that is neither grouped nor aggregated is a query error, not a default — the form has to make that unrepresentable rather than let the server refuse it. |
| TODO-F38 | Move the free-SQL derivation out of a table's action bar and onto the catalogue screen (`TablesView`), once the server route moves out from under `{tableId}` (`../back/todo.md` TODO-13). The SQL tab runs against **every** registered table, not the one whose page it is opened from — the same confusion that made the guided mode necessary, now confined to one tab instead of the whole feature, and `DeriveSqlForm`'s caption exists only to say so. Once the route is top-level: `DeriveTableModal` loses its tab pair and becomes the guided form alone, opened from `TableHeader`'s *Actions* menu under **Produire** as it is today; `DeriveSqlForm` moves under a new modal opened from `TablesView`'s own header, next to the catalogue it actually acts on; `useDeriveTable` splits along the same line or takes the route as a parameter. Run it in one pass with TODO-F35 — same breaking server release. |
| TODO-F33 | On `/tables/:tableId` nothing of the screen state reaches the URL, against §9: the applied filter is held as `activeFilterId` inside `components/filters/TableFilterBar.vue` and the grid's sort inside `useTableRows`, so a refresh drops both and the screen cannot be shared by copy-paste. `TablesView` and `SourcesView` already do it — they read their initial state through `queryString` from `utils/routeQuery.ts` and write it back with `router.replace` on change. Do the same for the table workspace: the applied filter's identifier and the sort, nothing else — the open modals, the edit session and the `Tableau / ⬛ / Carte` focus stay out, being ephemeral. Two traps: a filter identifier belongs to one table, so it has to be dropped by the same `tableId` watch that already resets `activeFilterId`, and an identifier read from the URL may name a filter the catalogue no longer holds — that resolves to no filter applied, never to an error |
