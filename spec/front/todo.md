> **Role** — the chantiers to run on `web/`: gaps between the rules of

> exception.
> What breaks a feature goes to [blockers.md](blockers.md); what is accepted to

> [improvements.md](improvements.md).

> Go server: [../back/todo.md](../back/todo.md) · Project: [../project/todo.md](../project/todo.md).

Each entry carries a stable identifier (`TODO-Fn`); a retired identifier is never reused. Entries are
grouped by nature, in decreasing order of impact within each group.

**How much to write.** An entry may be long. Detail is welcome here — it is what makes the chantier
implementable months later, by someone with no memory of the audit that found it: name the files and
the components concerned, say what to change and in what order, state the rules and invariants to
respect, and record the trap that produced the gap. Naming what exists is part of that: a component,
a composable, a type, a prop or an event are cited by name — that is a pointer into the code, not
code. Cite the file and the symbol, never a line number: it is stale the next time anyone touches
the file, and a wrong line sends the reader to the wrong place with confidence. A symbol is found by
search and stays true. What stays out is **code itself**: no snippet, no template fragment, no diff. Write the
instruction, not the patch — the code is written later, against the code as it is then.

## 1. Architecture and code

| # | Chantier |
|---|---|
| TODO-F35 | Realign `src/client/` on the single success envelope the server adopts (`../back/todo.md` TODO-8), which is a **breaking** change to every write route at once. Today each wrapper in `src/client/tables.ts`, `sources.ts` and `filters.ts` mirrors an envelope the server invented per route, and `src/client/types.ts` carries one DTO per shape; three routes resolve to `undefined` because a `204` and an empty body do so in `http.ts`, so nothing downstream can say what was deleted. The worst of it is `uploadSource`: `useSources.upload` tells a loaded upload from an unloaded multi-layer GeoPackage by probing for a `tableId` field on the response, and returns `{ tableId }` or `null` accordingly — a shape difference read as a discriminator, which the server side of the chantier replaces with an explicit one. Order: `types.ts` first (the one envelope type plus the discriminated upload outcome, §2 — no response type is ever declared in a resource module), then the wrappers, then the callers. The callers are where the gain lands: `useSources.upload` stops probing and switches on the discriminator; the delete flows in `useSources`, `useTableMetadata` and `useSavedFilters` can finally toast **what** was removed instead of a generic success, which is what §8.4 asks of a global action's result and what §8.3 asks of a destructive one. Two things stay out of the envelope and out of this chantier: the tile bytes and the streamed export, neither of which is JSON. Run it in one pass with TODO-F38, whose server side (`../back/todo.md` TODO-13) is the same breaking release |

## 2. User experience

| # | Chantier |
|---|---|
| TODO-F31 | `views/TableDetailView.vue` has no loading and no error state: every child is behind `v-if="table"`, and `useTableMetadata.loadAll` swallows a failure into a toast alone. A table whose metadata fails to load — or is merely slow — shows a breadcrumb over a blank page, and the only way back is a browser reload, which §0.18 and §8.1 both forbid (four explicit states, an error carrying a way to retry without reloading). Have `useTableMetadata` expose its `loading` and its `error` alongside `table` and `columns` instead of toasting, and have the view render `Skeleton` on the first load and `ErrorState` with a retry on the failure, the way `SourcesView` and `TableRowsPanel` already do. Keep the toast for the *mutating* actions (rename, delete, add column), where §8.4 puts a global action's result — it is only the load whose error has to stay on screen |
| TODO-F32 | Opening a modal moves focus to its ✕ close button rather than to its first meaningful field, against §8.5: `useFocusTrap.activate` focuses the first focusable element of the container, and `Modal.vue` renders the close button in its header, before the slot. So `Ajouter une colonne`, `Créer un filtre` and `Dériver une table` all open with the destructive-adjacent control focused and the user has to Tab into the form. Fix it in the trap rather than in each modal: focus the first focusable that is not the close control — mark that control so the trap can skip it — and keep the current behaviour for a modal whose slot has no focusable content at all (`GeometryModal`, `ConfirmDialog`). The Tab/Shift+Tab cycle and the focus restore on close stay as they are |
| TODO-F34 | Give the server's editable parameters a screen, once they leave `config.yaml` for a settings table (`../back/todo.md` TODO-3). Everything that is not needed to boot the process — the pagination defaults and caps, the body cap, the request timeout, the export batch size, the simplify/precision caps, the three caches' TTL and size, the sources' max size and allowed extensions — becomes readable and writable over the API, and the UI is the point of that chantier: today changing any of them means editing a file on the server and restarting it. A new route and a new view (`/settings`, `SettingsView`), a fourth entry in `App.vue`'s side navigation, a `src/client/settings.ts` module with its DTOs in `types.ts` (§2), and a `useSettings` composable holding the load, the draft and the save (§4) — the view assembles, it does not hold the logic. Requirements: the four screen states of §8.1, since this screen is a load like any other; the server validates and the form must surface a per-field refusal rather than one global error, so the save's error path has to carry the field it names; a saved change is a global action's result and toasts (§8.4); and the fields group by the same families the server does rather than as one flat list of twenty inputs. Two traps. A parameter the server calls boot-only must not be rendered as editable — the screen shows what is editable, and a read-only echo of `port` or `duckdb.path` next to editable fields reads as a form field that silently fails. And a cap the user lowers below a value the UI itself sends (`limit` on the paginated lists) makes the app start failing its own requests: the client reads those caps rather than hardcoding them |
| TODO-F36 | Surface the server's diagnostics endpoint (`../back/todo.md` TODO-12) — on-disk database size, buffer-manager pressure, temporary-file spilling, loaded extensions. It answers the question the status banner cannot: the server is up, but is it healthy. Where it goes depends on what TODO-F34 lands: if a `/settings` screen exists by then this is a second panel or a second tab of it rather than a fourth route, since both are "the server itself" rather than "the data". A `src/client/ops.ts` addition (that module already owns the probes and is the only caller of `getRoot`), a `useDiagnostics` composable, and presentational components under `components/ops/`. Requirements: §8.1's four states; the numbers are read, so they are formatted like the rest of the app's sizes (`formatSize` in `utils/sourceRows.ts`) rather than printed raw; and it refreshes on demand, never on a timer — a polling admin page is a background cost paid by every open tab, and §8.10 asks the opposite. It is a read-only screen: nothing here writes |
| TODO-F37 | Give the derivation modal an aggregation mode, once the server offers one (`../back/todo.md` TODO-14): group-by columns plus aggregate expressions. *Dériver* currently produces one derived row per source row, and grouping is the other thing a user derives for. It needs its own screen rather than a third tab on `DeriveTableModal`, whose column picker means "carry this column over" and would mean "group by this column" in the new mode — the same word for two different acts is exactly the confusion the guided mode was built to remove. What can be reused as is: `useDeriveTable` for the submit and the new table's name, `FilterNodeEditor` for the row conditions (the same tree, in the same place in the sequence), and the picker's exclusion of the geometry column and `__pkey`. What is new: the group-by column list and the aggregate rows, an aggregate row being an expression under an alias like `DeriveFromTableForm`'s computed-column rows already are. Trap: under a `GROUP BY` a column that is neither grouped nor aggregated is a query error, not a default — the form has to make that unrepresentable rather than let the server refuse it. Formerly IMP-F4 |
| TODO-F38 | Move the free-SQL derivation out of a table's action bar and onto the catalogue screen (`TablesView`), once the server route moves out from under `{tableId}` (`../back/todo.md` TODO-13). Run it in one pass with TODO-F35 — same breaking server release. Formerly IMP-F5 |
| TODO-F33 | On `/tables/:tableId` nothing of the screen state reaches the URL, against §9: the applied filter is held as `activeFilterId` inside `components/filters/TableFilterBar.vue` and the grid's sort inside `useTableRows`, so a refresh drops both and the screen cannot be shared by copy-paste. `TablesView` and `SourcesView` already do it — they read their initial state through `queryString` from `utils/routeQuery.ts` and write it back with `router.replace` on change.
