# Darow — Possible improvements (Go server)

> **Role** — undecided leads for the Go server: what would deserve doing, without the decision
> being made. Nothing here is planned. A lead taken up leaves this file and becomes an entry of
> [todo.md](todo.md); a lead dropped becomes an entry of [limitations.md](limitations.md) or
> disappears.
> Neighbours: [blockers.md](blockers.md) · [spec.md](spec.md) (architecture and contracts).
>
> Vue 3 UI: [../front/improvements.md](../front/improvements.md) · Project: [../project/improvements.md](../project/improvements.md).

Each entry carries a stable identifier (`IMP-n`); a retired identifier is never reused.

| # | Lead | Motivation | Reference |
|---|---|---|---|
| IMP-22 | Replace `internal/observer` with a plain `func(T)` callback field on the two services that notify. `Observer[T]` is a package, a type and a test for twenty-six lines, and both of its instantiations (`observer.Observer[storage.Metadata]` for a table's removal, `observer.Observer[storage.Settings]` for a settings change) are built in `core.NewServices` and given exactly one listener each | The generic buys the fan-out to several listeners that nothing registers, and costs a parameter threaded through `NewMetadataService` and `NewSettingsService` plus the `&observer.Observer[...]{}` literal every test setup in `internal/service` has to build to call them. A `func(storage.Metadata)` parameter takes `nil` in a test and reads the same at the wiring site. What has to be decided is whether the second listener is expected: `core` already registers two reactions to a table's removal behind one callback, so the fan-out has a plausible future | `spec.md` §1, §5.1, §5.8 |
| IMP-23 | Collapse the narrow ports `internal/service` declares over its own types. `schemaReader` (`derive.go`), `schemaReaderTyper` (`column.go`) and `columnTyper` (`rows.go`) are three interfaces over the same two `SchemaService` methods, and `metadataStore` (`derive.go`), `metadataImporter` (`import.go`) and `metadataRefresher` (`rows.go`) three more over `MetadataService` — all six declared and implemented inside the one package | The interface pattern of §1 exists to keep a consumer off a concrete type across a package boundary — that is what `handlers/ports.go` and `core.storageAdapter` do. Inside `service` there is no boundary to cross and no cycle to break, so the six names decouple nothing; what they do buy is a per-test double narrower than the service. What has to be decided is whether that testing convenience is worth six names for two concrete types, or whether one `schemaPort` and one `metadataPort` would carry the same doubles with a third of the vocabulary | `spec.md` §1, §5 |
| IMP-24 | Hang a private read on the `guest` role: give `guards.Guards` a read scope again and mount it on the routes an installation wants closed. Nothing in the code carries this today — `Guards` holds the write scope alone — so taking the lead means adding the scope, deciding **which** reads it covers (a whole table? the catalogue? `/diagnostics`?) and how an installation states that, since a global "reads are closed" switch is the one shape `limitations.md` LIM-20 already argues against | `types.RoleGuest` exists in the identity module and stands exactly where an anonymous caller stands: it reads everything, which everyone already may. The role is granted to *name* a reader, and naming a reader is only worth its cost the day a read is refused to someone. Two things in `spec.md` already point here: §6.5's `Cache-Control: public` on a tile stops being correct the day authorization goes finer than global and would become `private`, and §6.7's whole read/write split is stated as a global decision. What has to be decided first is whether a private read is a need of this product at all, or whether closing reads stays the job of whatever fronts the server (LIM-19, LIM-20) | `spec.md` §6.5, §6.7 |

A retired identifier is never reused, so the next lead recorded here takes `IMP-25`.
