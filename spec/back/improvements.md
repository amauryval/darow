# Darow — Possible improvements (Go server)

> **Role** — undecided leads for the Go server: what would deserve doing, without the decision
> being made. Nothing here is planned. A lead taken up leaves this file and becomes an entry of
> [todo.md](todo.md); a lead dropped becomes an entry of [limitations.md](limitations.md) or
> disappears.
> Neighbours: [blockers.md](blockers.md) · [spec.md](spec.md) (architecture and contracts).
>
> Vue 3 UI: [../front/improvements.md](../front/improvements.md) · Project: [../project/improvements.md](../project/improvements.md).

Each entry carries a stable identifier (`IMP-n`); a retired identifier is never reused.

| # | Lead | Motivation | Reference |
|---|---|---|---|
| IMP-7 | Guard a written geometry beyond parseability: reject an invalid ring/self-intersection (`ST_IsValid`) and, optionally, a type the table does not already hold (`GeoRepository.Types`) | A drawn polygon that closes badly is stored as is today and then breaks tiles and area computations downstream. Against: `geometryType` is deliberately not a stored fact (rule 10) and a table may legitimately mix types, so a type check is a preference the caller states, not an invariant the server owns — hence undecided | `spec.md` §5.2, rules 10 and 22 |
| IMP-1 | `catalog.MetadataReader.TableExists`: give it a caller or drop it from the contract | Present as a cheap existence primitive, with no production caller today — a contract carries what is used | `spec.md` §4.4 |
| IMP-3 | Stop storing `isGeo` and `geometryColumn` in `metadata` and derive both from `duckdb_columns()` when a table is resolved | Two catalogue config columns duplicate what the engine already knows and can disagree with it (BLK-1). `tables.TableColumns` + `GeometryColumn` already answer exactly this question, so the lead is now one call, not a new query. Against: `tables.Resolve` builds a table's identifiers from a cached `Metadata` with no query at all today, so deriving costs a catalogue read per resolution. `rowCount`, `bbox`, `createdAt`/`updatedAt`, `srid`, `sourceName`/`sourceLayer` are not derivable and stay whatever is decided | `spec.md` §4.1, §4.2, §4.8 |
| IMP-4 | Expose a diagnostics endpoint fed by DuckDB's own system tables — `pragma_database_size()`, `duckdb_memory()`, `duckdb_temporary_files()`, `duckdb_settings()`, `duckdb_extensions()` — for the admin UI | These answer questions the server cannot answer from its own state (on-disk size, buffer-manager pressure, whether a query is spilling to disk), at no scan cost. It is the only class of DuckDB-metadata read that buys something today: the row counts stay exact (`estimated_size` is a stale per-row-group estimate, measured 1,000,000 rows off right after a `DELETE` and still 16,960 off after a `CHECKPOINT`), so no `COUNT(*)` in the code can be replaced by one. Undecided: what is exposed, to whom, and whether it belongs to `/readyz`'s neighbourhood or to the business API | `spec.md` §4.8, §6.1 |
| IMP-5 | Extend the guided derivation (`/derive-from-table`) to aggregation: a `GROUP BY` over chosen columns with aggregate expressions (`COUNT(*)`, `SUM`, `ST_Union`) | The guided mode is row-wise today: one source row, one derived row. Aggregation is the other half of what a user derives a table for, but it changes the object's nature — cardinality, a fused geometry, the meaning of the regenerated `__pkey` — so it is a distinct shape rather than one more field on `DeriveSpec`, and it was deliberately kept out of the first pass | `spec.md` §8.1 |
| IMP-6 | Move the free-SQL `/tables/{tableId}/derive` to a top-level route, outside `{tableId}` | Its query is validated against **every** registered table, and it ignores the `{tableId}` it is nested under — the path states a scope the endpoint does not have. `/derive-from-table` is now the one that genuinely derives from the table in the path, which makes the mismatch on its neighbour easier to read as a mistake. Moving it is a breaking API change and a front change (`../front/improvements.md` IMP-F5), hence undecided | `spec.md` §6.1, §8 |
| IMP-2 | Give table creation the same transactional composition deletion already has: today the catalogue cascades on delete only, while the create sequence relies on `MetadataService.Rollback`'s compensating action | With attached repositories (TODO-3, TODO-4) the create path gains one more thing to undo per attachment, each a chance to leave a half-created table behind — deletion's guarantee comes from a transaction, creation's from remembering to compensate | `spec.md` §5.1, §5.4 |
