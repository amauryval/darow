# Darow — Possible improvements (Go server)

> **Role** — undecided leads for the Go server: what would deserve doing, without the decision
> being made. Nothing here is planned. A lead taken up leaves this file and becomes an entry of
> [todo.md](todo.md); a lead dropped becomes an entry of [limitations.md](limitations.md) or
> disappears.
> Neighbours: [blockers.md](blockers.md) · [spec.md](spec.md) (architecture and contracts).
>
> Vue 3 UI: [../front/improvements.md](../front/improvements.md) · Project: [../project/improvements.md](../project/improvements.md).

Each entry carries a stable identifier (`IMP-n`); a retired identifier is never reused.

**The *Worth doing — and when* column** is the audit's own verdict on the lead, and it is not the
decision: it says whether the lead looks worth its cost today, and names the **signal** that would
settle it — a second listener, a seventh port, a deployment that cannot close its reads upstream.
A trigger is an observable event, never a date and never "when there is time". A lead whose signal
fires stops being a lead: it leaves for [todo.md](todo.md) with a new `TODO-n`, or for
[limitations.md](limitations.md) if the signal is what rules it out.

| # | Lead | Motivation | Worth doing — and when | Reference |
|---|---|---|---|---|
| IMP-22 | Replace `internal/observer` with a plain `func(T)` callback field on the two services that notify. `Observer[T]` is a package, a type and a test for twenty-six lines, and both of its instantiations (`observer.Observer[storage.Metadata]` for a table's removal, `observer.Observer[storage.Settings]` for a settings change) are built in `core.NewServices` and given exactly one listener each | The generic buys the fan-out to several listeners that nothing registers, and costs a parameter threaded through `NewMetadataService` and `NewSettingsService` plus the `&observer.Observer[...]{}` literal every test setup in `internal/service` has to build to call them. A `func(storage.Metadata)` parameter takes `nil` in a test and reads the same at the wiring site. What has to be decided is whether the second listener is expected: `core` already registers two reactions to a table's removal behind one callback, so the fan-out has a plausible future | **Not on its own.** Unwinding it touches two constructors and six test setups for no behaviour change, against a fan-out `core` already uses once. Fold it into a change already touching `NewServices`'s wiring or a notifying service's signature. The signal that settles it the other way: a listener registered on either observer from outside `core` — the generic is right then, and this lead retires | `spec.md` §1, §5.1, §5.8 |
| IMP-23 | Collapse the narrow ports `internal/service` declares over its own types. `schemaReader` (`derive.go`), `schemaReaderTyper` (`column.go`) and `columnTyper` (`rows.go`) are three interfaces over the same two `SchemaService` methods, and `metadataStore` (`derive.go`), `metadataImporter` (`import.go`) and `metadataRefresher` (`rows.go`) three more over `MetadataService` — all six declared and implemented inside the one package | The interface pattern of §1 exists to keep a consumer off a concrete type across a package boundary — that is what `handlers/ports.go` and `core.storageAdapter` do. Inside `service` there is no boundary to cross and no cycle to break, so the six names decouple nothing; what they do buy is a per-test double narrower than the service. What has to be decided is whether that testing convenience is worth six names for two concrete types, or whether one `schemaPort` and one `metadataPort` would carry the same doubles with a third of the vocabulary | **Not on its own** — unwinding six ports touches every double in the package for no behaviour change. The trigger is additive rather than painful: the next service needing `Schema`/`Types` or a `MetadataService` method would make a seventh port. Collapse them in **that** change, instead of adding to the pile | `spec.md` §1, §5 |
| IMP-24 | Hang a private read on the `guest` role: give `guards.Guards` a read scope again and mount it on the routes an installation wants closed. Nothing in the code carries this today — `Guards` holds the write scope alone — so taking the lead means adding the scope, deciding **which** reads it covers (a whole table? the catalogue? `/diagnostics`?) and how an installation states that, since a global "reads are closed" switch is the one shape `limitations.md` LIM-20 already argues against | `types.RoleGuest` exists in the identity module and stands exactly where an anonymous caller stands: it reads everything, which everyone already may. The role is granted to *name* a reader, and naming a reader is only worth its cost the day a read is refused to someone. Two things in `spec.md` already point here: §6.5's `Cache-Control: public` on a tile stops being correct the day authorization goes finer than global and would become `private`, and §6.7's whole read/write split is stated as a global decision. What has to be decided first is whether a private read is a need of this product at all, or whether closing reads stays the job of whatever fronts the server (LIM-19, LIM-20) | **Not a decision anyone has to take yet**, and not a code decision at all — a product one. Until an installation has to refuse a read to a named caller, the honest answer stays LIM-19/LIM-20's: closing reads is the job of whatever fronts this server. The signal is a real deployment that cannot do that upstream — never a wish for symmetry with the write guard, which is what put `GuestScope` in the code for nothing once already | `spec.md` §6.5, §6.7 |

A retired identifier is never reused, so the next lead recorded here takes `IMP-25`.
