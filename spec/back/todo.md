# Darow — Identified debt (Go server)

> **Role** — the chantiers to run on the Go server: gaps between [spec.md](spec.md) and the code,
> structural debt, non-blocking fixes. Each row is work engaged or to be engaged, not a tolerated
> exception. What blocks a use goes to [blockers.md](blockers.md); what is accepted and will not be
> fixed to [limitations.md](limitations.md); what is not decided yet to
> [improvements.md](improvements.md).
>
> Vue 3 UI: [../front/todo.md](../front/todo.md) · Project:
> [../project/todo.md](../project/todo.md).

Each entry carries a stable identifier (`TODO-n`); a retired identifier is never reused.

**How much to write.** An entry may be long. Detail is welcome here — it is what makes the chantier
implementable months later, by someone with no memory of the audit that found it: name the files and
the symbols concerned, say what to change and in what order, state the constraints and invariants to
respect, and record the trap that produced the gap. Naming what exists is part of that: an
interface, a type, a method, a package are cited by name — that is a pointer into the code, not
code. Cite the file and the symbol, never a line number: it is stale the next time anyone touches
the file, and a wrong line sends the reader to the wrong place with confidence. A symbol is found by
search and stays true. What stays out is **code itself**: no snippet, no full signature, no diff.
Write the instruction, not the patch — the code is written later, against the code as it is then.

**Order of work.** The two entries are independent, with one preference:
TODO-18 before TODO-14 if both are taken, since the two share the expression machinery
and TODO-18 is the one that extracts the AST validator out of `Materializer` into a form a second
caller can use. TODO-14 is the largest chantier here and the only one whose shape is still partly
open.

**Front counterparts.** TODO-14 and TODO-18 each have a matching chantier in
[`../front/todo.md`](../front/todo.md) — TODO-F37 and TODO-F44. Neither may be started before its
server side exists: a shape written on the screen before the API serves it is written twice, which is
the drift the entries exist to end.

| TODO-18 | A column's values cannot be rewritten **in place**: the only writes to row data are `RowRepository.Update` (the same values on a named set of pkeys) and `UpdateMany` (its own values per row), both keyed by pkey and both sized by what a client can page through, so rewriting a column over a whole table means reading every pkey and issuing page after page of `PATCH /rows` — and nothing at all computes the new value from the old one. What already exists is the *derivation* half and it is deliberately not the same act: `service.ComputedColumn` (`service/derive_from_table.go`) already carries a free scalar expression under an alias, so a concatenation, an arithmetic combination and a `CASE WHEN` assignment are all reachable today — but only through `CreateFromQuery`, which produces a **new, frozen table** (§8). The user who wants a column cleaned up gets a second table instead: a new `tableId`, its stored filters gone (the `Filters` attachment cascades on create, it does not copy), its per-table settings gone (§4.10), every saved URL and every map pointing at the old one. Add the in-place form: **transform a column's values**, on the table in hand, over the rows a filter names. Shape it as a new `service.ColumnService` (`service/column.go`) — not on `SchemaService`, which is structure and not data (§5.3), and not on `RowService`, whose whole contract is typed per-row CRUD keyed by pkey (§5.2) — holding ports onto `SchemaService` (schema and types), `MetadataService` (`RefreshDerived`) and the `sizeGuard`. Its input is one target column plus an ordered list of cases, a case being a `[]FilterCondition` tree and the assignment applied to the rows it matches, plus a default assignment for the rest and the row conditions restricting which rows are touched at all — that ordered list, rendered as a single `CASE WHEN`, is what "assign values according to conditions" means, and it must be one statement rather than one write per case, or two overlapping cases would depend on the order they landed in. An assignment is a discriminated union with exactly one arm set: a constant, a concatenation of ordered parts (each a column reference or a literal), an arithmetic operation over two operands with a whitelisted operator, and a free scalar expression — the last arm being the same escape hatch `ComputedColumn` is, and for the same reason (`COALESCE`, the string functions and the spatial functions are what a transform is wanted for, and no widget form reaches them). Constraints, none of them optional: every column reference is whitelisted against `SchemaService.Schema` and quoted with `QuoteIdentifier`, every literal is a **bound parameter** including inside the `CASE` arms (the bind order across the WHEN, the THEN and the outer WHERE is exactly where an off-by-one silently writes the right value into the wrong rows, so the assembly returns its args with the fragment it rendered, never alongside it); the row conditions and each case's conditions go through `BuildFilter` with the geometry column excluded, like `whereFor` already does (rule 5); the geometry column is **never** a target — a geometry write carries its own encoding and its own CRS and passes the family and validity guards (rules 22, 23, §5.2), all three of which a bulk expression bypasses — and neither is a column `storage.IsHiddenColumn` names; the case count and the expression length are bounded like `maxComputedColumns` is. The gate every arm passes, whichever it is: the rendered assignment is checked by **DuckDB's own parser**, through the very walk `/derive` uses — an UPDATE's SET expression may carry a scalar subquery, so the free-expression arm has exactly the reach of a free SELECT, and leaving it unchecked would put `read_csv`/`read_text` behind a write route when rule 4 keeps them out of a read one. Do it by extracting the body of `Materializer.validateDeriveQuery` (`duckdb/tables/create_from_query.go`) into a package-level function over `Querier` and `physicalNamesReader`, called both by the materializer and by the new path, and validate the assignment by probing it as a SELECT over the physical table; writing a second, weaker validator for the write path is the trap this entry exists to prevent. The same probe answers "if the type allows it": `queryColumns` (`duckdb/tables/introspection.go`) describes the probe without running it, so the expression's result type is known before any write and can be refused against the column's declared type from `SchemaService.Types` with a `ValidationError` naming both, instead of surfacing as the 500 a failed UPDATE would be; the arithmetic arm refuses a non-numeric operand structurally on top of that, which is what lets a UI offer the arm only where it applies. Storage side: one new method on `storage.RowRepository` taking the rendered assignment, the WHERE and their args and returning the number of rows written — a **single** `UPDATE` statement through the adapter's `Exec`, hence serialized behind its table's write scope (rule 21) and atomic on its own (rule 6), never a per-row loop; plus a filtered count for the preview, which `TableRepository.Count` has no form of today. `tables.Open` gains the physical-names reader as a third dependency exactly as `NewMaterializer` already takes it, wired in `duckdb.New` from `a.catalog`, and `storage/mocks` gains every new method. Two routes on `TablesHandler` next to `AddColumn` and `GetDistinctValues`, resolved through `TableResolver` and `ColumnValidator` (check that the validator already excludes the geometry and the hidden columns before relying on it): the transform itself, and a **preview** returning the matched row count and a bounded sample of before/after values. Keep them two routes rather than one flag — a preview flag on a write route is precisely how a preview ends up writing. After a successful write, call `RefreshDerived` with `touchesGeometry` false (rule 9): `rowCount` has not moved but `UpdatedAt` must, and that is not cosmetic — the MVT tile cache is keyed on `UpdatedAt` (rule 20) and a tile requested with `attrs` embeds the very column that just changed, so skipping it serves stale attribute tiles. The schema cache is left alone: nothing structural changed, so no `InvalidateSchema`. A concatenation over a text column grows the database, so this is a data-growing write in `sizeGuard`'s sense — `Check` before, `Grew` after, like `RowService`'s own writes. Nothing here is undoable and there is no history: the preview route is what stands in for an undo, and that is a scope decision to record in `limitations.md` when this lands, not a gap to fill. Ships with its tests (rule 17), the swagger annotations (§6.6), the §6.1 route table, its own service section, and `spec/index.md` in the same change. | TODO-14 | The guided derivation is row-wise only: `service.DeriveSpec` (`service/derive_from_table.go`) produces at most one derived row per source row, so the other half of what a user derives a table for — a count per category, a summed value per zone, a fused geometry per group — has no path at all short of hand-written SQL. Extend it to aggregation: `GROUP BY` over chosen columns, with aggregate expressions (`COUNT(*)`, `SUM`, `ST_Union`). Make it a **distinct shape**, not extra fields on `DeriveSpec`: it changes the object's nature — the cardinality, a geometry that is fused rather than carried, and the meaning of the `__pkey` `CreateFromQuery` regenerates — and `projectionFor`'s current contract (an empty column list means every column, the geometry appended on its own) is exactly wrong under a `GROUP BY`, where an unaggregated column is a query error rather than a default. What carries over unchanged: the grouped columns are whitelisted against `SchemaService.Schema` and quoted with `QuoteIdentifier` like the carried ones; the row conditions stay the same `[]FilterCondition` tree through `whereFor`/`BuildFilter` with its values bound (rule 5); the assembled query goes through the very same `CreateFromQuery`, hence the same DuckDB AST validation (rule 4) and the same materialization tail (§7 steps 3, 6, 7); every rejection is a `ValidationError` raised before the catalogue row exists. Two things to settle: whether aggregate expressions are a free scalar expression under an alias like `ComputedColumn` is today — the same argument applies, no widget form reaches `ST_Union` — and what happens to `isGeo` when the group produces no geometry at all. Largest chantier in this file; take it last.
