# Darow — Identified debt (Go server)

> **Role** — the chantiers to run on the Go server: gaps between [spec.md](spec.md) and the code,
> structural debt, non-blocking fixes. Each row is work engaged or to be engaged, not a tolerated
> exception. What blocks a use goes to [blockers.md](blockers.md); what is accepted and will not be
> fixed to [limitations.md](limitations.md); what is not decided yet to
> [improvements.md](improvements.md).
>
> Vue 3 UI: [../front/todo.md](../front/todo.md) · Project:
> [../project/todo.md](../project/todo.md).

Each entry carries a stable identifier (`TODO-n`); a retired identifier is never reused.

**How much to write.** An entry may be long. Detail is welcome here — it is what makes the chantier
implementable months later, by someone with no memory of the audit that found it: name the files and
the symbols concerned, say what to change and in what order, state the constraints and invariants to
respect, and record the trap that produced the gap. Naming what exists is part of that: an
interface, a type, a method, a package are cited by name — that is a pointer into the code, not
code. Cite the file and the symbol, never a line number: it is stale the next time anyone touches
the file, and a wrong line sends the reader to the wrong place with confidence. A symbol is found by
search and stays true. What stays out is **code itself**: no snippet, no full signature, no diff.
Write the instruction, not the patch — the code is written later, against the code as it is then.

**The one exception**, taken deliberately and recorded as such: the appendix at the end of this file
holds TODO-16's `internal/observer` type in full. The reason is particular to that entry — its six
constraints each _reject_ a part of the shape the observer pattern is normally written in, and
stating the constraints without showing what survives them invites the rejected version straight
back. It is not a precedent: any other entry that feels like it needs a snippet needs better names
instead. The appendix goes away the day the package exists.

**Order of work.** The entries are independent unless one says otherwise. What follows is the plan
established by the audit of 2026-08-06, which took up every lead `improvements.md` held (IMP-1
through IMP-7 became TODO-9 through TODO-15) and left that file empty.

0. **The blockers come first**, before any entry below — [blockers.md](blockers.md)'s own rule. All
   three (BLK-3, a deleted table leaving its source displayed as loaded; BLK-2, a DuckDB `INTERNAL`
   error leaving `Adapter` handing out connections onto a dead instance; BLK-1, no type allowlist on
   `POST /tables/{tableId}/columns`) are fixed. BLK-1 landing is also what makes TODO-10 worth doing
   at all — a `GEOMETRY` column added behind the catalogue's back is exactly the disagreement
   TODO-10 removes the possibility of — so TODO-10 now has one less case to reconcile.
1. **TODO-9 before TODO-3.** TODO-3 attaches a second table to the catalogue, and TODO-9 is what
   makes an attachment safe to add on the _create_ path; doing them the other way round means
   writing a compensating action that TODO-9 then deletes.
2. **TODO-8 and TODO-13 together, as one API-contract pass.** Both change the REST contract and both
   force the front to be realigned; done separately the front pays the realignment twice. This is
   the one pass in the plan that is breaking, and it should be a single one.
3. **TODO-10, TODO-11, TODO-12, TODO-15 and TODO-16 are independent** of everything else and of one
   another. TODO-15 is minutes of work and can be taken at any point. TODO-16 is worth taking early
   despite not being a blocker: it is what stops BLK-3's shape from recurring, and every entry that
   adds a cache or a catalogue-attached repository (TODO-3, TODO-10, TODO-12) adds a potential
   consumer to it.
4. **TODO-14 last.** It is the largest single chantier here, it is additive, and it is the only one
   whose shape is still partly open.

TODO-3 creates a new table attached to the catalogue through `duckdb/catalog.Catalog.Register` and

| TODO-9  | Table creation has no transactional guarantee, while deletion does. `duckdb/catalog.Catalog.Remove` runs the metadata row, the physical table (through its `Dropper`) and every registered `Attachment` inside one `*sql.Tx`; creation is a four-step sequence in `service/derive.go` and `service/import.go` (catalogue row → materialize → `UpdateMetadata` → `RefreshDerived`) whose only recovery is `MetadataService.Rollback`, a compensating action called from nine distinct failure sites across those two files. A compensating action that itself fails leaves a catalogue row without a physical table — the very state `Catalog.TableExists` and `PhysicalNames` now have to cross-check `duckdb_tables()` to paper over (§4.4). Give the create path the same shape as the delete path: one transaction owned by `duckdb/catalog`, into which the materialization and the metadata finalisation are both enrolled, so a failure at any step unwinds by rollback rather than by remembering to compensate. Two constraints. First, DuckDB's DDL is transactional, so the CTAS, the indexes and the Hilbert clustering (`duckdb/tables`'s `create_from_file.go`, `create_from_query.go`, `indexes.go`) can join the transaction — but they currently take the adapter's `writeMu` per statement, and one transaction spanning them must take it once for its whole duration, exactly as `BulkInsert` and `Catalog.Remove` already do (rule 21, §4.6). Second, `duckdb/catalog` and `duckdb/tables` never import each other: the materialization must reach the transaction the way the `Dropper` already does — a function value wired in `duckdb.New` — not by one package naming the other. Once this lands, `MetadataService.Rollback` and its nine call sites go, and `Catalog`'s contract loses the compensating-action vocabulary. While here, generalize `Attachment` from its delete-only `DeleteAttached` into a lifecycle contract covering creation too, since that is exactly what the transactional create path has to fan out to: it is already an observer registry in everything but name (`Register` at construction, a `children` list, fan-out inside the transaction), and TODO-3's settings repository will be its second implementer. It stays **transactional and storage-side**, carrying `context.Context` and the `*sql.Tx`, aborting at the first error — that is what separates it from the in-memory service-layer notifier of TODO-16, which fires after the commit and carries neither. The two must not be merged. Do this **before** TODO-3: every attachment added to the catalogue is one more thing the create path would otherwise have to undo by hand. | TODO-16 | A table's removal has to be told to a growing set of in-memory caches, and the wiring is hand-made per consumer, so a consumer gets forgotten: BLK-3 is that, `SourceService`'s cache never learning a table is gone. Today `MetadataService.RemoveTable` invalidates its own LRU and calls `schemaInvalidator.InvalidateSchema` — one narrow port, one consumer, hardcoded — and BLK-3's narrow fix is a second port of the same shape, which makes the third omission a matter of time. Replace it with one **generic in-memory lifecycle notifier** in a package of its own, `internal/observer`: an `Observer[T]` holding one registered-callback list per event and fanning out to it, generic over the observed type so it stays free of any domain vocabulary. It is injected into `MetadataService` at wiring time by `core.NewServices`, with `SchemaService` and `SourceService` registering onto it. The six constraints below are the specification of that type — where they contradict the textbook shape of the pattern (a callback returning an `error`, an `errors.Join` over the fan-out, a create/update/delete triplet offered whether or not anything listens), the constraint wins and the textbook shape is what produced the wrong version. The type it lands on is written out **after this table**, as this file's one deliberate exception to its own no-code rule. What that buys: `core/core.go` becomes the single place that states who reacts to a table's disappearance, instead of that being spread across each service's port list. Four constraints, each of which the obvious implementation gets wrong. **(a) Service layer only, never storage** — see TODO-9's note: the delete cascade runs inside a `*sql.Tx` and its `Attachment` contract stays as it is; this notifier fires **after** the transaction has committed, on in-memory state alone. Two mechanisms with two different guarantees, and conflating them would put cache eviction inside a transaction that may still roll back. **(b) No `context.Context`, deliberately, and this is the one place that reads as a rule-23 violation without being one**: rule 23 requires ctx of what touches DuckDB or the disk, and an observer that only evicts a map entry touches neither — `SourceService.List` and `MaxUploadBytes` are the existing precedent. A callback that wants to query is a design error, not a missing parameter. **(c) A callback returns nothing, not an error.** Every consumer this notifier has or will plausibly have evicts a map entry or patches a slice under its own mutex — `SchemaService.InvalidateSchema` already returns nothing — so there is no failure to report, and an `error` return would create one where none exists: the table is _already deleted and committed_ by the time the fan-out runs, and letting a cache eviction turn a successful `DELETE` into a 5xx would tell the client the deletion failed when it did not. It also dissolves the question of whether to join the errors or stop at the first: joining them defeats `response.MapServiceError`'s `errors.As`/`errors.Is` dispatch (§6.4), and stopping at the first leaves the later consumers stale, but neither arises once nothing can fail. A callback that genuinely needs to fail is doing work that does not belong after a commit. **(d) Registration at construction only.** The server is concurrent by nature; a registry appended to while requests are in flight is a data race on the callback slice. Register in `NewServices` and never after, exactly as `duckdb/catalog.Catalog.Register` already does. **(e) The observed payload is `storage.Metadata`, not a `tableId`** — and getting there fixes a contract violation on the way. `MetadataService.RemoveTable` takes a bare `tableId` today while §4.2's access contract says a storage-touching call takes the `Metadata` the caller already resolved; `handlers.TablesHandler.DeleteTable` in fact holds the full `meta` from `ResolveTable` and passes `meta.TableId` alone, throwing away exactly what the fan-out needs. `SchemaService` only wants the id, but `SourceService` wants `SourceName`/`SourceLayer` to find the entry to unmark, and rediscovering them by scanning its slice for a matching `TableId` is the kind of reverse lookup the payload should make unnecessary. Move `RemoveTable` onto the access contract first; the notifier then carries what is already in hand. **(f) The notifier is owned by `core`, not by `MetadataService`.** The object graph forbids the obvious placement: `NewServices` builds `schemaSvc`, then `metadataSvc` over it, then `importSvc` over that, then `sourceSvc` over `importSvc` — so making `MetadataService` the subject that `SourceService` subscribes to closes a cycle, forcing registration after construction, where a constructor no longer states its own dependencies (§1's narrow-interface-plus-conformance-assertion pattern exists to stop that). Have `core.NewServices` build the notifier, inject it into `MetadataService` as the thing it _notifies_, and register `SchemaService` and `SourceService` onto it as the things that _listen_. Nobody then holds anybody, `core/core.go` becomes the one file naming who reacts to what, and `MetadataService` loses `schemaInvalidator` — which §5.1 currently has to call out as its single dependency on another service. Two events to leave out until something needs them: update (nothing wants the old and new metadata side by side — the tile cache is keyed on `UpdatedAt`, and §3.2 deliberately links a source to its table by `sourceName`, never by the renameable `tableName`, so a rename has no listener) and create (`SourceService` already updates its own cache in `Load`, which it initiates, and a `/derive` table has no source). ## Appendix — TODO-16's `internal/observer`

> **This is the one place in `spec/` that holds code**, by an explicit decision taken when TODO-16
> was written, against this file's own rule above. It is here because the type is small enough to
> state in full and because the six constraints of TODO-16 reject the shape the pattern is usually
> written in — naming the constraints without showing what survives them invites the textbook
> version back. It is **not** a licence for a second snippet: every other entry keeps to names.
>
> If the code below and TODO-16's constraints ever disagree, **the constraints are right** — this
> block is a rendering of them, not a second source of truth. Delete this appendix the day the
> package exists: the code is then its own description.

```go
// Package observer notifies callbacks registered at wiring time of an item's
// lifecycle events. It is in-memory only: it runs after the write it reports
// has been committed, and it touches neither the database nor the disk.
package observer

// Observer fans an observed item out to the callbacks registered on it.
// Generic over the observed type, so it carries no domain vocabulary.
//
// Registration is not safe for concurrent use, and deliberately so: every
// callback is registered while the services are wired, none once requests are
// in flight, exactly as duckdb/catalog.Catalog.Register already works.
type Observer[T any] struct {
	removed []func(T)
}

// OnRemoved registers fn, to be called with an item that has been removed.
func (o *Observer[T]) OnRemoved(fn func(T)) {
	o.removed = append(o.removed, fn)
}

// NotifyRemoved calls every registered callback with the removed item.
//
// It returns nothing. The removal is already committed by the time this runs,
// so a callback has nothing left to veto, and reporting a failed cache
// eviction as the operation's error would answer 5xx for a DELETE that in
// fact succeeded.
func (o *Observer[T]) NotifyRemoved(item T) {
	for _, fn := range o.removed {
		fn(item)
	}
}
```

Three things to read off it, each of them a constraint of TODO-16 made visible:

-   **One event, not three.** No `NotifyCreate`, no `NotifyUpdate`: neither has a listener today or
    a foreseeable one, and adding an event to this type later is four lines.
-   **`func(T)`, not `func(T) error`** — hence no `errors.Join`, and no import at all.
-   **`Removed`, not `Deleted`**, to stay on the vocabulary `spec.md` §4.4 fixes: `Catalog.Remove`
    removes a whole table, `RowRepository.Delete` deletes rows. What is observed here is the table.

`MetadataService` holds one `*observer.Observer[storage.Metadata]` and notifies it;
`core.NewServices` builds it, registers `SchemaService` and `SourceService` onto it, and is then the
single file stating who reacts to a table's removal.
