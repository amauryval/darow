# Darow — Identified debt (Go server)

> **Role** — the chantiers to run on the Go server: gaps between [spec.md](spec.md) and the code,
> structural debt, non-blocking fixes. Each row is work engaged or to be engaged, not a tolerated
> exception.
> What blocks a use goes to [blockers.md](blockers.md); what is accepted and will not be fixed to
> [limitations.md](limitations.md); what is not decided yet to
> [improvements.md](improvements.md).
>
> Vue 3 UI: [../front/todo.md](../front/todo.md) · Project: [../project/todo.md](../project/todo.md).

Each entry carries a stable identifier (`TODO-n`); a retired identifier is never reused.

**How much to write.** An entry may be long. Detail is welcome here — it is what makes the chantier
implementable months later, by someone with no memory of the audit that found it: name the files and
the symbols concerned, say what to change and in what order, state the constraints and invariants to
respect, and record the trap that produced the gap. Naming what exists is part of that: an
interface, a type, a method, a package are cited by name — that is a pointer into the code, not
code. Cite the file and the symbol, never a line number: it is stale the next time anyone touches
the file, and a wrong line sends the reader to the wrong place with confidence. A symbol is found by
search and stays true. What stays out is **code itself**: no snippet, no full signature, no diff. Write the
instruction, not the patch — the code is written later, against the code as it is then.

**Order of work.** The entries are independent unless one says otherwise.

TODO-5 (collapsing the multi-backend abstraction) comes first: it moves or deletes the very packages
TODO-3, TODO-4 and TODO-6 write into, and doing it after them means writing the same code twice.
TODO-6 (DuckDB's native catalogue) is independent of TODO-5 but reads better after it, since it
touches `duckdb/data` only. TODO-3 (settings table) and TODO-4 (stored filters) are independent of
one another and can be picked up in either order — both create a new table attached to the catalogue
through `Catalog.Register` and `duckdb/catalog`'s per-component migration registry.

| TODO-5 | **Collapse the multi-backend abstraction of `internal/storage` onto DuckDB** (LIM-9). What exists today: `storage/catalog` and `storage/data` declare `MetadataReader`/`MetadataWriter`/`MetadataManager`, `Catalog`, `Attachment`, `TableResolver`, `TableRepository`, `RowRepository`, `GeoRepository`, `TableLifecycle` and `SourceIntrospector`, each with exactly one implementation, in `duckdb/catalog` and `duckdb/data`; `storage/sort` exists only to break the import cycle those two contract packages create, and `storage/sort.go` re-exports it as `storage.SortField`/`storage.ParseSort`; `catalog.UnitOfWork` is an alias for `any` to avoid naming `*sql.Tx`; `duckdb/adapter.go`, `duckdb/table.go` and `duckdb/lifecycle.go` are some sixteen methods that only forward to `a.catalog` or `a.lifecycle`; `storage.SQLWrapper` has no production caller at all (only the conformance harness); `storagetest` is a suite written to run "against any adapter" and wired to the single one. Order of work: **(1)** delete the forwarding layer — have `core.storageAdapter` and each service's narrow port reach the concrete `*duckdb.Adapter` through accessors (`Catalog()`, plus the equivalent for the lifecycle and the resolver) instead of re-declaring every method on `Adapter`; **(2)** move `Metadata`, `MetadataPatch`, `SourceKey`, `Attachment`, `RowQuery` and `FeatureQuery` into the packages that own them and retire `storage/catalog` and `storage/data` as separate contract packages, turn `UnitOfWork` into `*sql.Tx`, fold `storage/sort` back into `storage` and drop the alias file; **(3)** delete `storage.SQLWrapper` and `storagetest`, but only after checking behaviour by behaviour that each assertion of `catalog_suite.go` and `data_suite.go` is covered by a test in `duckdb/catalog` or `duckdb/data` — move over what is not, nothing gets lost; **(4)** update `spec.md` §1, §4.4, §4.6 and §9 in the same change, since they state the multi-backend premise and list the packages being removed. | TODO-6 | **Read structure from DuckDB's own catalogue functions instead of `DESCRIBE` and hand-rolled introspection** (LIM-9 makes engine-specific catalogue access legitimate). `duckdb/data/schema.go`'s `DescribeColumns` is the single point every column listing goes through, and it interpolates its target into a `DESCRIBE` statement. Split its two uses: for a **table** target, query `duckdb_columns()` filtered by a bound `table_name` — the physical name stops being interpolated at all (rule 1 becomes structurally satisfied rather than validated after the fact), and the row carries `column_index`, `data_type`, `is_nullable` and `column_default` instead of two strings; for a **query** target, keep a `DESCRIBE`-on-a-select path, because a query that has not been materialized has no catalogue entry — this is what `duckdb/data/lifecycle.go` relies on in `findGeometryColumn`, `parseGeometryCRS` (§7.2) and the `__pkey` collision check (§8).
