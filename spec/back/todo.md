# Darow — Identified debt (Go server)

> **Role** — the chantiers to run on the Go server: gaps between [spec.md](spec.md) and the code,
> structural debt, non-blocking fixes. Each row is work engaged or to be engaged, not a tolerated
> exception.
> What blocks a use goes to [blockers.md](blockers.md); what is accepted and will not be fixed to
> [limitations.md](limitations.md); what is not decided yet to
> [improvements.md](improvements.md).

> Vue 3 UI: [../front/todo.md](../front/todo.md) · Project: [../project/todo.md](../project/todo.md).

Each entry carries a stable identifier (`TODO-n`); a retired identifier is never reused.

**How much to write.** An entry may be long. Detail is welcome here — it is what makes the chantier
implementable months later, by someone with no memory of the audit that found it: name the files and
the symbols concerned, say what to change and in what order, state the constraints and invariants to
respect, and record the trap that produced the gap. Naming what exists is part of that: an
interface, a type, a method, a package are cited by name — that is a pointer into the code, not
code. Cite the file and the symbol, never a line number: it is stale the next time anyone touches
the file, and a wrong line sends the reader to the wrong place with confidence. A symbol is found by
search and stays true. What stays out is **code itself**: no snippet, no full signature, no diff. Write the
instruction, not the patch — the code is written later, against the code as it is then.

**Order of work.** The entries are independent unless one says otherwise. Two sequences are imposed
today, both on the storage layer:

*Catalogue side:*

1. **TODO-5** — move the catalogue aggregate and its attachment contract into `storage/catalog`.
2. **TODO-6** — turn the migrations into a per-component registry.
3. **TODO-3** (settings table) and **TODO-4** (stored filters), in either order, once 1 and 2 have
   landed.

TODO-3 and TODO-4 both create a new table attached to the catalogue. Written before TODO-5 and
TODO-6, each one would be bound to DuckDB and would have to duplicate its DDL inside the metadata
component — work that TODO-5 and TODO-6 would then have to undo twice.

*Data side:*

1. **TODO-7** — give the physical table's lifecycle (create, index, cluster, drop) a contract in
   `storage/data`. It shares a seam with TODO-5: the catalogue's cascade must obtain the drop from
   that contract instead of writing the DDL itself, so land TODO-5 first, or the two together.
2. **TODO-8** — split source-file introspection out of `TableCreator`. Independent of the rest, but
   it comes before **TODO-2** (tabular formats), which adds a format on exactly that seam.

| TODO-5 | **The catalogue aggregate has no backend-agnostic contract.** `internal/storage/catalog` declares only the value type `Metadata` and the `MetadataManager`/`MetadataReader`/`MetadataWriter` interfaces — the *aggregate* that actually orchestrates the catalogue lives entirely in the DuckDB package: `Catalog`, its `Register` extension point, the `Deleter` interface and `DeleteTable` in `internal/storage/duckdb/catalog/catalog.go`. Two consequences. First, `Deleter.DeleteTx` is typed on `database/sql`'s transaction type, so the very extension point meant to receive future catalogue-attached repositories is not engine-agnostic: a second adapter cannot implement it, and a repository written against it is bound to DuckDB. Second, `PhysicalNames` (`duckdb/catalog/metadata.go`), which is what enforces rule 4's "may only reference already registered tables" for `/derive`, is declared in no contract at all — `duckdb/derive.go` reaches for it on the concrete `Catalog`. **What to do**, in order: (1) move the aggregate's vocabulary into `internal/storage/catalog` — a `Catalog` contract carrying the metadata surface plus `PhysicalNames` and the whole-table delete, and an engine-neutral attachment contract replacing `Deleter` (the unit of work must be an opaque handle owned by the adapter, not `*sql.Tx`, so that the transaction stays the adapter's business); (2) keep `duckdb/catalog.Catalog` as the implementation of that contract, unchanged in behaviour — one transaction covering the physical `DROP`, every attached repository and the metadata row, under the adapter's `writeMu`; (3) declare on the adapter an accessor returning the catalogue aggregate, and have `core.storageAdapter` depend on that rather than on a flattened `MetadataManager` — today every catalogue method is promoted onto `Adapter` itself, so each new attached repository would widen the adapter's method set instead of hanging off the catalogue; (4) update `spec.md` §4.4's contract table and §4.6, and extend `storagetest`'s catalogue conformance suite to cover the cascade through a registered attachment, which no test exercises today. **Constraints**: `Register` must stay a construction-time call (registering after the fact reintroduces the risk of a forgotten dependent), and the cascade must remain one transaction — a partial deletion is unobservable today and must stay so. **The trap**: the extension point was designed ahead of its first user, so nothing forced it through the contract package, and `Register` still has no production caller. **Order: this is step 1 of the catalogue sequence** — it comes first, before TODO-6, and both come before TODO-3 and TODO-4, which are its first two users | A new table attached to the catalogue can only be written against DuckDB, and the contract package no longer describes the catalogue it claims to abstract | `spec.md` §4.4, §4.6 |
| TODO-6 | **Schema migrations are hardcoded to the `metadata` table alone.** `internal/storage/duckdb/catalog/migrations.go` holds one flat, append-only list of statements, all of them against `metadata`, applied against a single global integer in the `schema_version` table; the creation DDL lives separately in `metadataSchema` (`duckdb/catalog/metadata.go`) and a fresh database is seeded straight at the list's length. There is no seam for a second catalogue table to declare its own creation DDL and its own ordered migrations: adding one means editing the metadata package's globals, and the fresh-database shortcut means the new table's DDL must be written **twice** — once in the creation schema, once as an appended migration — with nothing detecting an omission, since a fresh database never replays and an existing one never runs the creation DDL. **What to do**: introduce, in `duckdb/catalog`, a registry to which each catalogue component contributes a creation DDL and an ordered migration list, and make `Migrate` iterate over the registered components; track a version per component in `schema_version` (add a component column, and migrate the existing single row to the `metadata` component) rather than one number for the whole database, so components can be added without renumbering. Keep the two properties `Migrate` already has: a brand-new database is seeded at the latest version instead of replaying, and a duplicate-column error on an `ADD COLUMN` is tolerated for databases predating version tracking (`execMigration`). Update `spec.md` §4.6's migrations bullet once done. **Order: this is step 2 of the catalogue sequence** — after TODO-5, before TODO-3 and TODO-4, which both need a table created through this registry |
| TODO-7 | **The physical table's lifecycle has no contract, only its access does.** `internal/storage/data` abstracts reading and writing an *existing* table cleanly — `TableResolver` resolves a `Metadata` once, `TableRepository` fans out to `RowRepository` and `GeoRepository`, and nothing engine-typed crosses the boundary. Creating, indexing and dropping that same table escape it entirely, in three different directions. (a) Creation sits on `TableCreator`, declared in the root `storage` package (`aggregate.go`) rather than in `data`, and implemented on `Adapter` itself in `duckdb/create.go` and `duckdb/derive.go` instead of in `duckdb/data`. (b) The drop is raw DDL built inside `duckdb/catalog/catalog.go`'s `DeleteTable` — the catalogue package writing data-table DDL, which is the same cross-layer reach TODO-5 removes on the other side. (c) The physical guarantees rule 19 states — the RTREE index, the `__pkey` unique index, the Hilbert clustering, and the rule that clustering rebuilds the table so both indexes must be created *after* it — live only as private methods on `Adapter` (`createSpatialIndex`, `createPkeyIndex`, `clusterByHilbert`); no contract names them, so a second adapter has nothing telling it they are mandatory. **What to do**, in order: (1) declare in `storage/data` a lifecycle contract covering materialization of a physical table, its post-creation indexing, and its drop, alongside the existing access contracts; (2) implement it in `duckdb/data`, moving `create.go`'s and `derive.go`'s bodies there and leaving `Adapter` as what its own doc comment claims — connection, write serialization, wiring; (3) have the catalogue's cascade obtain the drop through that contract rather than formatting the DDL itself; (4) extend `storagetest`'s data conformance suite to assert the post-creation state a compliant adapter owes (indexes present, clustering applied on a geo table), which is asserted today only in DuckDB-specific tests. **Constraints**: keep the ordering invariant — clustering rebuilds the table, so indexes are created after it, never before; keep the drop inside the cascade's single transaction. **The trap**: `data` was extracted for the access path, which was the painful one, and the lifecycle stayed where it had always been. **Order**: shares a seam with TODO-5 (step 3 needs the attachment contract) — land TODO-5 first, or both together | The rules that make a table usable (indexes, clustering) are enforced by one file's convention rather than by a contract, and the catalogue writes data-table DDL | `spec.md` §4.2, §4.4, §4.6, rule 19 |
| TODO-8 | **`TableCreator` carries three unrelated concerns.** As declared in `internal/storage/aggregate.go`, it holds `CreateFromFile`, `CreateFromQuery`, `ListLayers` and `DetectCRS`. The last two are source-file introspection — enumerating a GeoPackage's layers, reading a layer's declared CRS — and have nothing to do with materializing a table: they answer questions about a file on disk, before any table exists, and `SourceService`/`ImportService` use them for previewing a source. They sit together only because DuckDB happens to answer both through `ST_Read`/`ST_Read_Meta`. `CreateFromFile` then mixes both halves in one call: it reads the file, detects or applies the CRS, reprojects, and materializes. **What to do**: split the interface in two — a source-introspection contract (layers, declared CRS) and a table-materialization contract (from a source, from a SELECT) — and let each consumer depend on the one it uses; the ports in `service/import.go` and `service/source.go` already narrow to subsets, so they mostly shrink. Keep `CreateFromFile`'s behaviour intact, reprojection included: the CRS it resolves is what §7 depends on, and the failure-rather-than-guess rule when a geo source declares no CRS must survive the split. **Why it matters beyond tidiness**: an adapter that does not read files through GDAL must today implement layer enumeration to satisfy an interface it only needs for table creation. **Order**: independent, but do it before TODO-2 — adding a tabular format touches exactly this seam, and doing it after means writing the new format into the interface twice | An adapter must implement file-format introspection to satisfy a table-creation contract, and the seam a new format lands on is the one that is mis-cut | `spec.md` §4.4, §7 | Every new catalogue-attached table has to edit the metadata component's globals and duplicate its DDL, with a silent failure mode when the two copies diverge | `spec.md` §4.6 |
