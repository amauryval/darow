# Darow — Identified debt (Go server)

> **Role** — the chantiers to run on the Go server: gaps between [spec.md](spec.md) and the code,
> structural debt, non-blocking fixes. Each row is work engaged or to be engaged, not a tolerated
> exception. What blocks a use goes to [blockers.md](blockers.md); what is accepted and will not be
> fixed to [limitations.md](limitations.md); what is not decided yet to
> [improvements.md](improvements.md).
>
> Vue 3 UI: [../front/todo.md](../front/todo.md) · Project:
> [../project/todo.md](../project/todo.md).

Each entry carries a stable identifier (`TODO-n`); a retired identifier is never reused.

**How much to write.** An entry may be long. Detail is welcome here — it is what makes the chantier
implementable months later, by someone with no memory of the audit that found it: name the files and
the symbols concerned, say what to change and in what order, state the constraints and invariants to
respect, and record the trap that produced the gap. Naming what exists is part of that: an
interface, a type, a method, a package are cited by name — that is a pointer into the code, not
code. Cite the file and the symbol, never a line number: it is stale the next time anyone touches
the file, and a wrong line sends the reader to the wrong place with confidence. A symbol is found by
search and stays true. What stays out is **code itself**: no snippet, no full signature, no diff.
Write the instruction, not the patch — the code is written later, against the code as it is then.

**Order of work.** The entries are independent unless one says otherwise. What follows is the plan
established by the audit of 2026-08-06, which took up every lead `improvements.md` held (IMP-1
through IMP-7 became TODO-9 through TODO-15) and left that file empty.

1. **TODO-8 and TODO-13 together, as one API-contract pass.** Both change the REST contract and both
   force the front to be realigned; done separately the front pays the realignment twice. This is
   the one pass in the plan that is breaking, and it should be a single one.
2. **TODO-10 and TODO-11 are independent** of everything else and of one another. BLK-1's fix (a type
   allowlist on `POST /tables/{tableId}/columns`) is what makes TODO-10 worth doing at all — a
   `GEOMETRY` column added behind the catalogue's back is exactly the disagreement TODO-10 removes
   the possibility of — so TODO-10 now has one less case to reconcile.
3. **TODO-14 last.** It is the largest single chantier here, it is additive, and it is the only one
   whose shape is still partly open.

**Front counterparts.** Three entries here have a matching chantier in
[`../front/todo.md`](../front/todo.md), which must not be started before its server side exists:
TODO-8 → TODO-F35, TODO-14 → TODO-F37, TODO-13 → TODO-F38.

| TODO-8  | Success responses have no common shape, and one route's `201` is ambiguous. Six routes answer a write with an empty body — `DELETE /tables/{tableId}`, `DELETE /sources/{name}` and `DELETE /tables/{tableId}/rows/{pkey}` return a bare `204`, `/healthz` and `/readyz` a bare `200` — so a client can only infer success from the status code and has nothing to show the user about what was actually done. The others each invent their own envelope (`{tables,total,limit,offset}`, a bare `metadataDTO`, `{tableId}`, `{name,type}`, `{pkeys}`, `{row}`). Worst case: `POST /sources/upload` answers `201` with **two different shapes** on the same route — a `service.Source` when the upload is a multi-layer GeoPackage left unloaded, `{tableId}` when it was loaded — and the only way to tell them apart is probing for a field, which is what `web/src/composables/useSources.ts`'s `upload` does today. Decide one success envelope, carrying at minimum what happened and on which object (the deleted table's name and id, the number of rows removed, the loaded layer), give the two upload outcomes an explicit discriminator instead of a shape difference, and replace the `204`s with it. Handlers concerned: `tables.go` (`DeleteTable`), `sources.go` (`DeleteSource`, `UploadSource`), `rows.go` (`DeleteRow`). Keep `GET /tiles/...`'s binary body and the streamed export out of it — they are not JSON. Align `web/src/client/` plus the toast wording that consumes it (`../front/todo.md` TODO-F35) | TODO-10 | `isGeo` and `geometryColumn` are stored as `metadata` config columns while DuckDB's own catalogue already holds the same fact, and the two can disagree — that disagreement is BLK-1's payload. Stop storing them and derive both when a table is resolved: `duckdb/tables/introspection.go`'s `tableColumns` plus `soleGeometryColumn` already answer exactly this question (they are what `CreateFromFile` step 3 uses to detect the geometry column in the first place), so the chantier is one call at resolution time, not a new query to write. Order: first make the two derived at the point of use, then drop the columns from the `metadata` DDL through a `duckdb/catalog` migration on the `metadata` component — whose `Migrations` list is empty today (LIM-7), so this is the first entry it gets and the first real exercise of the per-component registry. The trap and the reason this was a lead rather than a decision: `duckdb/tables`' `resolve` builds a table's identifiers from an already-cached `storage.Metadata` with **no query at all**, and it runs on every single data access — deriving costs one catalogue read per resolution on the hottest path in the server. Decide where that read is absorbed (the resolution middleware `router/validation/resolver.go` reads metadata once per request already, and `MetadataService`'s LRU is the natural place to keep the derived pair) before touching the DDL. `rowCount`, `bbox`, `createdAt`/`updatedAt`, `srid`, `sourceName`/`sourceLayer` are **not** derivable and stay stored exactly as they are. | TODO-11 | A written geometry is checked for its **family** (rule 23, `service/geometry_family.go`) but never for its **validity**: a polygon whose ring self-intersects or fails to close is stored as is, and then breaks tile rendering and every area computation downstream, with nothing on the write path having said so. Add an `ST_IsValid` guard next to the family check — same place, same request-scoped shape: `RowService`'s `checkGeometryFamily` already resolves the written geometries once per request from `storage.GeometryValue`, so validity joins it rather than becoming a second pass. Constraints: the refusal is a `service.ValidationError` (400) raised **before** anything is written, batch included, exactly as the family refusal is; the check runs on the geometry as the server will store it, i.e. after `ST_GeomFromText`/`ST_GeomFromGeoJSON` and the `ST_Transform` of rule 22, not on the literal; and the message must name what is wrong in terms a drawing user can act on (`ST_IsValidReason` is what carries that) rather than relaying the engine's phrasing. The cost is the reason this was a lead: one `ST_IsValid` per written geometry on every write, paid on the hot path of an edit session that saves many rows at once. No front chantier is needed — a 400 already reaches the save toast through `errorMessage`; what the front gains is a message worth reading. | TODO-13 | `POST /tables/{tableId}/derive` states a scope it does not have. Its query is validated against **every** `physicalName` registered in `metadata` and it ignores the `{tableId}` it is nested under entirely — the path reads as "derive from this table" and the endpoint means "derive from anything". Its neighbour `/tables/{tableId}/derive-from-table` is the one that genuinely derives from the table in the path, which makes the mismatch easier to read as a mistake than it was when free SQL was the only mode. Move the free-SQL route out from under `{tableId}` to a top-level one in `router/routes.go`, drop the `TableResolver` it embeds for nothing (`router/validation/resolver.go`), and adjust `handlers.TablesHandler.DeriveTable`'s signature and its swagger annotation accordingly — `DeriveService.DeriveTable` itself already takes no source table and needs no change. This is a **breaking** API change: run it in the same pass as TODO-8, so the front realigns once rather than twice (`../front/todo.md` TODO-F38), and regenerate `docs/` with `swag init` in the same change. | TODO-14 | The guided derivation is row-wise only: `service.DeriveSpec` (`service/derive_from_table.go`) produces at most one derived row per source row, so the other half of what a user derives a table for — a count per category, a summed value per zone, a fused geometry per group — has no path at all short of hand-written SQL. Extend it to aggregation: `GROUP BY` over chosen columns, with aggregate expressions (`COUNT(*)`, `SUM`, `ST_Union`). Make it a **distinct shape**, not extra fields on `DeriveSpec`: it changes the object's nature — the cardinality, a geometry that is fused rather than carried, and the meaning of the `__pkey` `CreateFromQuery` regenerates — and `projectionFor`'s current contract (an empty column list means every column, the geometry appended on its own) is exactly wrong under a `GROUP BY`, where an unaggregated column is a query error rather than a default. What carries over unchanged: the grouped columns are whitelisted against `SchemaService.Schema` and quoted with `QuoteIdentifier` like the carried ones; the row conditions stay the same `[]FilterCondition` tree through `whereFor`/`BuildFilter` with its values bound (rule 5); the assembled query goes through the very same `CreateFromQuery`, hence the same DuckDB AST validation (rule 4) and the same materialization tail (§7 steps 3, 6, 7); every rejection is a `ValidationError` raised before the catalogue row exists. Two things to settle: whether aggregate expressions are a free scalar expression under an alias like `ComputedColumn` is today — the same argument applies, no widget form reaches `ST_Union` — and what happens to `isGeo` when the group produces no geometry at all. Largest chantier in this file; take it last. Front counterpart: `../front/todo.md` TODO-F37.
