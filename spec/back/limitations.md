# Darow — Accepted limitations (Go server)

> **Role** — what the Go server deliberately does not do. These are not defects to fix but scope
> decisions, listed here so that a caller knows where it stands. A limitation that is lifted leaves
> this file and becomes an entry of [todo.md](todo.md).
> Neighbours: [blockers.md](blockers.md) · [improvements.md](improvements.md) ·
> [spec.md](spec.md) (architecture and contracts).
>
> Vue 3 UI: [../front/limitations.md](../front/limitations.md) · Project: [../project/limitations.md](../project/limitations.md).

Each entry carries a stable identifier (`LIM-n`); a retired identifier is never reused.

| # | Limitation | Consequence for the caller | Reference |
|---|---|---|---|
| LIM-1 | No authentication, no authorization, no CORS, no rate limiting — every write route is open | Rules out direct exposure on the Internet. Deploy on a trusted network, or behind a reverse proxy that carries these functions | `spec.md` §6.7 |
| LIM-2 | A table with several geometry columns is rejected at import | A multi-geometry file must be split upstream; the whole domain assumes a single geometry per table | `spec.md` §7 |
| LIM-3 | Writes concerning one table are serialized: each names a `storage.WriteScope` and takes that scope's lock (`duckdb/write_locks.go`), held over `Exec` and over `WithTx` for a whole transaction. Writes to different tables run in parallel. Serializing within a scope is a deliberate choice, not an engine constraint: DuckDB runs concurrent writer threads under MVCC plus optimistic concurrency control, where appends never conflict and only two edits reaching the same row do | A bulk insert into one table no longer blocks a single-cell update on another, but two writes to the *same* table still queue, so a table's own write throughput does not grow with cores. What is bought with it is that no caller ever meets a transaction-conflict error, so the server carries no retry path at all. Reads are untouched: `Query`/`QueryRow` take no lock | `spec.md` §0 rule 21, §4.6 |
| LIM-15 | A DuckDB database file is held under an exclusive file lock: a second process opening it read-write is refused outright, so exactly one server instance can serve a given database | Running two instances against one database is not a coordination problem to solve but a start-up failure — the second refuses to open rather than corrupting anything. Redundancy or a rolling restart therefore means one database per instance, or another engine, which LIM-9 rules out. DuckDB's own answers to this (the Quack remote protocol, DuckLake behind an external catalogue) are out of scope | `spec.md` §4.6 |
| LIM-4 | Geometry is reprojected once at import to EPSG:3857, and every read route outputs `OGC:CRS84`. Only **export** takes an arbitrary output CRS (`?srid=`, §5.6) | A tile, a GeoJSON read, a bbox or an OGC Features response is lon/lat and nothing else: on-demand reprojection exists for a file being written out, never for a route being read | `spec.md` §4.6, §5.6 |
| LIM-16 | An exported file does not state its CRS from the inside. DuckDB's GEOMETRY carries no SRID, so the GeoParquet metadata it writes omits the `crs` key entirely and a reader applies the format's default, `OGC:CRS84`; GeoJSON is read as lon/lat by RFC 7946 whatever it holds | An export in any CRS other than lon/lat is only identified by its **file name** (`communes_EPSG2154.parquet`, §5.6). Renaming the file loses that, and a tool reading it blind will place the coordinates as degrees. Exporting in the default lon/lat is the only self-describing option | `spec.md` §5.6 |
| LIM-5 | The `simplify`/`precision` parameters are ignored on the MVT route (tolerance is derived from the zoom) | They only apply to the GeoJSON routes, and do not enter the tile cache key | `spec.md` §4.7 |
| LIM-6 | `TRY(...)` plus `WHERE mvt_geom IS NOT NULL` around `ST_AsMVTGeom` silently drops the features that upstream clipping corrupts (`duckdb/duckdb-spatial#792`) | A tile may omit a feature without saying so; the net can only drop an already broken feature, never a valid one | `spec.md` §4.7 |
| LIM-7 | The per-component migration registry (`duckdb/catalog/migrations.go`) exists and is exercised, but no database created before the current pre-1.0 development phase is guaranteed to migrate cleanly | Until the server reaches its first stable release, a schema change may require recreating the database rather than upgrading it in place; the registry is validated forward from the current schema, not against arbitrary historical shapes | `spec.md` §4.6 |
| LIM-9 | DuckDB is the only storage engine, and the only one that will be supported — the backend-portability premise (a second adapter behind engine-agnostic contracts) is dropped | The server's SQL, its spatial functions and its catalogue may rely on DuckDB-specific behaviour, including DuckDB's own catalogue functions. Porting to another engine is a rewrite of the storage layer, not the implementation of an existing contract | `spec.md` §4.4, §4.6 |
| LIM-8 | `.xls`/`.xlsx` is not a supported source format | A spreadsheet must be exported to CSV before it can be loaded — DuckDB has no native Excel reader, unlike CSV/Parquet/GeoParquet which it (or GDAL) reads directly | `spec.md` §3.1, §7 |
| LIM-11 | A database created before a pagination limit became one stored page size per family keeps its `max*Limit` columns, now unread, and reads its page sizes off the `default*Limit` columns that release left behind | The `max*Limit` columns are inert (never read, never written); the `default*Limit` columns are read as the page sizes they are named for, whatever value that release left in them — which may not be the value its operator last set on the `max*Limit` side. `PATCH /api/v1/settings` with the three page sizes sets them straight, and the settings screen shows what is actually applied. Not migrated, under LIM-7's pre-1.0 rule | `spec.md` §2.5, §4.9 |
| LIM-12 | Two of the runtime-editable settings stay global and take no per-table override, unlike the rest (§2.5.1): `defaultListLimit`, which pages the catalogue listings — a page of *tables* belongs to no table — and `cacheTTLSec`, which is the lifetime of a process-wide LRU built once at startup and swapped whole when it changes (§5.8), not a per-table quantity | A table's settings cover its own pages and its own geometry output; changing how many tables a catalogue page holds, or how long the metadata/schema caches keep an entry, stays a single global decision on `PATCH /api/v1/settings` | `spec.md` §2.5.1, §5.8 |
| LIM-13 | `datetime` is not a supported OGC API - Features query parameter | The model has no notion of a temporal column, so a client cannot filter a collection's items by time | `spec.md` §6.2 |
| LIM-14 | Tiles are served only under the internal `/tables/{tableId}/tiles/{z}/{x}/{y}` route (§4.7, §6.1); no OGC API - Tiles (OGC 20-057) facade is exposed | A generic OGC-aware client (QGIS's "OGC API - Tiles" connector, another SIG tool) cannot discover or consume tiles from this server without knowing Darow's own URL shape. Considered and declined in the audit of 2026-08-09: it would have been an additive facade at the same MVT bytes, but its path order (`{tileMatrix}/{tileRow}/{tileCol}`, Y before X) is not the plain `{z}/{x}/{y}` template Leaflet/MapLibre/OpenLayers substitute natively, so serving it would only have helped an external client whose actual need was never confirmed — unlike OGC API - Features (§6.2), kept because collections/items already double as a documented, standards-based read path | `spec.md` §4.7, §6.1 |
| LIM-10 | An invalid written geometry's refusal names the literal that failed, not what is wrong with it | DuckDB's spatial extension has no `ST_IsValidReason` (unlike PostGIS) — only `ST_IsValid`. A caller sees which geometry was refused, not whether it self-intersects, has an unclosed ring, or another cause | `spec.md` §5.2 |
| LIM-17 | An in-place column transform (`POST .../columns/{col}/transform`, §8.3) has no undo and no history — once the `UPDATE` commits, the previous values are gone | `POST .../transform/preview` is the mitigation: it renders and type-checks the exact same assignment and reports a matched-row count plus a before/after sample before anything is written, so a caller can check the effect first. There is no server-side way to reverse a transform after the fact | `spec.md` §5.11, §8.3 |
| LIM-18 | A guided aggregation (`POST .../aggregate-from-table`, §8.2) has no `HAVING` — its `Conditions` filter rows before grouping, not groups after | Filtering on an aggregated value (e.g. "only zones summing over 100") needs a second pass: aggregate first, then `/derive-from-table` or `/filter` on the result | `spec.md` §8.2 |
