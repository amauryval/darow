# CLAUDE.md

## Purpose

Darow — a Go cartographic server backed by DuckDB (spatial extension). Serves sources, tables, rows,
MVT tiles, and SQL-derived tables over a REST API, plus a Vue3 admin UI embedded in the binary.

## Repo map

-   `cmd/server` : entrypoint (`main.go`) — loads config, opens DuckDB, wires services, router, UI
-   `internal/config` : YAML config (`config.yaml`), defaults, `--workdir` flag override
-   `internal/core` : wiring — builds the services and the LRU caches from the config
-   `internal/storage` : the storage layer's types, primitives and interfaces —
    `ValidateIdentifier`/`QuoteIdentifier`, `BuildFilter`, typed errors,
    `Metadata`/`Row`/`ColumnInfo`/`GeoFeature`/`GeoQuery`/`SortField`, and the `Catalog`,
    `TableRepository`/`RowRepository`/`GeoRepository` and `TableMaterializer` interfaces DuckDB
    implements; `mocks/` (testify) alongside
-   `internal/storage/duckdb` : the single implementation — `Adapter` (connection, `writeMu` write
    serialization, `WithTx`, and the `Catalog()`/`Materializer()`/`Table()` accessors), CTAS table
    creation with RTREE indexing and Hilbert clustering, `/derive`; sub-packages `catalog/` (the
    `metadata` table, migrations, transactional cascade delete, `Register`) and `tables/`, one file
    per family — `ref.go` (identifier resolution), `table.go`/`rows.go`/`geo.go` (the three
    repositories), `clauses.go`/`scan.go` (shared SQL fragments and row scanning), `materializer.go`
    split into `create_from_file.go`/`create_from_query.go`/`crs.go`/`indexes.go` plus the stateless
    `drop.go`, and `introspection.go` — the single place DuckDB's own catalogue functions
    `duckdb_columns`/`duckdb_indexes`/`duckdb_tables`/`duckdb_extensions` are read
-   `internal/service` : one service per concern (`MetadataService` owns the metadata cache,
    `SchemaService`, `RowService`, `GeoService` tile cache keyed on table `UpdatedAt`,
    `SourceService`, `ImportService`, `DeriveService`, `ExportService`)
-   `internal/router` : `chi` router, middlewares, `/ui` SPA + Swagger mounting (`webui.go`), with
    `handlers/` (one per endpoint family + the ports to the services), `validation/` (`{tableId}`
    resolution, column-name validation) and `response/` (JSON writing, error → status mapping)
-   `internal/webui` : `go:embed` of the Vue3 UI's production build (`dist/`) — generated by
    `mise run ui-build`, never hand-edited; `dist/index.html` is a tracked placeholder until built
-   `web` : Vue3 + TypeScript + Tailwind admin UI (Vite). `src/client/` is a typed REST client
    (`http.ts`, `tables.ts`, `sources.ts`, `geo.ts`) kept separate from
    `src/views/`/`src/components/` — app code always goes through the client, never raw `fetch`.
    Built output goes straight to `internal/webui/dist` (see `vite.config.ts`), not `web/dist`
-   `spec/` : the hand-written documentation, one directory per domain — `spec/back/` for the Go
    server, `spec/front/` for the Vue 3 admin UI, `spec/project/` for everything outside both
    (product identity and naming, repository layout, toolchain, `mise` tasks, Docker, CI, the
    outward-facing docs). The three are disjoint; back and front only touch through the REST API.
    All three are written in English, and hold the same five independent files:
    -   `spec.md` : the **stable** architecture document — contracts and invariants of the current
        code, code-free, written to be read by an agent; the code is the source of truth, this
        describes it. Changes only when the code changes
    -   `blockers.md` : what breaks correct use — fix before any new feature
    -   `limitations.md` : what is deliberately not done — scope decisions, not defects
    -   `todo.md` : identified debt — gaps between the spec and the code
    -   `improvements.md` : uncommitted leads, to be decided before being planned
-   Each of these files always exists, even with no entry — an empty one states so explicitly.
    Entries carry stable ids (`BLK-n`, `LIM-n`, `TODO-n`, `IMP-n`, `-Fn` for the front, `-Pn` for
    the project); a retired id is never reused. An audit's findings go into these four files, never
    into a spec — follow the `audit` skill for any audit, review pass, or recording of findings
-   `docs/` : generated Swagger only — `docs.go`/`swagger.json`/`swagger.yaml`, produced by
    `swag init` (see Commands). Never hand-edit these, never add hand-written docs here

## Rules

-   Instructions describe and must describe (if updated) the state of the related code. It does not
    contain information about the past or old choices.
-   Before any Go change, follow the `go-implementation` / `go-testing` skills.
-   Never launch dev processes (`go run`, `mise run run-dev`, `mise run ui-dev`, `npm run dev`) on
    your own initiative — ask the user to run them, or confirm first.
-   Before any Vue3 changes, read `spec/front/spec.md` and follow the `vue3-implementation` skill.
-   Never verify UI changes yourself via a browser or browser-automation tool — build/type-check
    (`mise run ui-build`) and let the user verify visually.
-   Business logic lives in composables (`src/composables/`) or pure functions (`src/utils/`), never
    in a `.vue` file; components are reusable and presentational (props in / events out); a view
    orchestrates and is split into sub-views as soon as it carries a second responsibility.
-   UI style: simple, uncluttered, professional — daisyUI as the base, wrapped in `components/ui/`
    primitives; views use Tailwind for layout only and never re-type a button's or field's classes
-   Git commands that change state (`commit`, `push`, `checkout`, `merge`, `rebase`, `reset`,
    `stash`, `worktree add/remove`, `branch -D`, ...) are forbidden unless explicitly requested.
-   Every new/changed struct, interface, method, or handler ships with its test in the same change,
    in a test file named after the file under test (`rows.go` → `rows_test.go`); a package's shared
    doubles and fixtures go in its `fixtures_test.go`, and each package's tests stand on their own
    without a sibling package's help changes do not need accompanying vitest tests unless explicitly
    asked for.
-   Any SQL identifier (table/column) interpolated into a query must go through
    `storage.ValidateIdentifier` first; values are always bound parameters, never interpolated.

## Commands

-   `mise run test` — run all Go tests
-   `mise run test-race` — run tests with the race detector
-   `mise run lint` — `go vet` + `gofmt`
-   Never pass `./...` to the go tool here. It enumerates every package in the module tree, imported
    or not, so it picks up `web/node_modules/flatted/golang/pkg/flatted` — a third-party Go package
    shipped by npm. It gets tested and vetted, never linked (the binary is only `cmd/server`'s
    import graph, and `internal/webui` embeds `dist/` alone), but it wastes CI time and can fail
    `gofmt` on code we don't own. The tasks above filter the package list explicitly
    (`go list ./... | grep -v /web/`) and scope `gofmt` to `cmd internal docs` — do the same in any
    ad-hoc `go test`/`go vet`/`gofmt` invocation
-   `mise run ui-install` / `ui-build` / `ui-dev` — web UI deps / production build (into
    `internal/webui/dist`) / Vite dev server
-   `mise run ui-lint` / `ui-test` — eslint / vitest for the web UI
-   `mise run build` — build the server binary (regenerates docs and UI first)
-   `mise run run-dev` — run the server against `config.yaml` (regenerates docs and UI first)
-   CI (`.github/workflows/ci.yml`) runs `go vet`/`gofmt`, `go test -race`, `ui-lint`/`ui-test`/
    `ui-build` (via `vue-tsc`/`vitest`/`vite`), and a Docker image build on every push/PR
-   `Dockerfile` — multi-stage build (UI → Go binary → slim runtime image); see also `.dockerignore`
